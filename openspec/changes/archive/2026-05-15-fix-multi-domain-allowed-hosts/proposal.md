# Change: Allow Multiple Public Domains via Coolify UI Env Vars

## Why

Production at `https://fastjob.es/` is currently returning Django's `DisallowedHost`:

> Invalid HTTP_HOST header: 'fastjob.es'. You may need to add 'fastjob.es' to ALLOWED_HOSTS.

The operator already set `ALLOWED_HOSTS=fastjob.es,fastjob.apps.darideveloper.com` in the
Coolify UI (with both *Buildtime* and *Runtime* checked), but the value never reaches Django.

Root cause: `docker-compose.yml` hardcodes three host-related variables to be **derived**
from Coolify's `SERVICE_FQDN_WEB`, and the Compose `environment:` block has higher precedence
than project-level env vars of the same name. The result is that the UI value is silently shadowed.

The current `docker-compose.yml` (web service) defines:

- `docker-compose.yml:52` — `ALLOWED_HOSTS=${SERVICE_FQDN_WEB},localhost,127.0.0.1`
- `docker-compose.yml:68` — `SITE_DOMAIN=${SERVICE_FQDN_WEB}`
- `docker-compose.yml:90` — `CSRF_TRUSTED_ORIGINS=https://${SERVICE_FQDN_WEB}`

Because Coolify's `SERVICE_FQDN_WEB` is a **single** FQDN (the Coolify-managed
`fastjob.apps.darideveloper.com`), `fastjob.es` never makes it into Django's host check.
The same hardcoding silently breaks two adjacent concerns even when the host check passes:

- `SITE_DOMAIN` is used to build absolute URLs (password-reset emails, OAuth callbacks,
  Stripe redirects, sitemap, unsubscribe links) — all currently emitted against the
  Coolify subdomain instead of the canonical `fastjob.es`.
- `CSRF_TRUSTED_ORIGINS` will reject any in-app POST submitted from `fastjob.es`
  (login, profile save, any user-facing form). Stripe webhooks are CSRF-exempt
  (signature-verified), but if Stripe is configured to call the `fastjob.es` URL they
  would still hit the `ALLOWED_HOSTS` failure above.

The Django side (`config/settings.py:11`, `:108`, `:360`) already parses these vars
correctly via `python-decouple` + `Csv()`. No code change is required there.

## What Changes

Make the three host-related env vars in `docker-compose.yml` **opt-overrideable** by the
Coolify UI (or by a developer's local `.env`), while keeping the current
`SERVICE_FQDN_WEB`-derived behavior as a fallback so first-boot Coolify imports continue
to work with zero manual configuration.

Concretely, switch from unconditional assignment to the `${VAR:-<fallback>}` form on the
`web` service:

- `ALLOWED_HOSTS=${ALLOWED_HOSTS:-${SERVICE_FQDN_WEB},localhost,127.0.0.1}`
- `SITE_DOMAIN=${SITE_DOMAIN:-${SERVICE_FQDN_WEB}}`
- `CSRF_TRUSTED_ORIGINS=${CSRF_TRUSTED_ORIGINS:-https://${SERVICE_FQDN_WEB}}`

Apply the same `${VAR:-…}` override pattern to the matching entries in the `celery_worker`
and `celery_beat` services (they were aligned in change `fix-celery-site-url-env`; we need
to keep them in lockstep so absolute URLs generated by background tasks use the canonical
domain too).

Add a short README/deployment note describing the **production-only** Coolify variables
the operator must declare for multi-domain deployments. Local development is unaffected
because the `${VAR:-…}` fallback collapses to today's behavior when the override is unset,
and the developer's `.env` (per `.env.example:3,37,69`) already supplies the right values.

## Impact

### Affected specs
- `specs/infrastructure/spec.md` — `Dynamic Host Security` requirement is too narrow
  today (single FQDN). It will be **MODIFIED** to mandate that operator-supplied
  `ALLOWED_HOSTS` / `CSRF_TRUSTED_ORIGINS` / `SITE_DOMAIN` override the auto-derived
  defaults when set, and to require the multi-domain case.

### Affected code
- `docker-compose.yml`
  - `web` service: lines 52, 68, 90 (`ALLOWED_HOSTS`, `SITE_DOMAIN`,
    `CSRF_TRUSTED_ORIGINS`).
  - `celery_worker` service: line 117 (`SITE_DOMAIN` only; `ALLOWED_HOSTS` and
    `CSRF_TRUSTED_ORIGINS` are not — and should not be — defined for a non-HTTP
    service).
  - `celery_beat` service: line 151 (`SITE_DOMAIN` only; same scope rule as worker).
- `.env.example` — clarify the three vars with a short comment block stating they are
  the override knobs for production multi-domain deployments.
- No Python code changes. No migrations. No test changes (existing tests use the Django
  test client and do not exercise the host header — confirmed in
  `apps/accounts/tests/test_url_surface.py:7`).

### Operator-side actions (production rollout)
Documented in `tasks.md` but summarized here:
1. In Coolify → Project → Environment variables, set (Runtime checked):
   - `ALLOWED_HOSTS=fastjob.es,fastjob.apps.darideveloper.com,localhost,127.0.0.1`
   - `CSRF_TRUSTED_ORIGINS=https://fastjob.es,https://fastjob.apps.darideveloper.com`
   - `SITE_DOMAIN=fastjob.es`
2. Redeploy.

### Non-impact
- Local `docker compose up` with the developer's existing `.env` continues to work
  unchanged — the override vars in `.env` win, and if absent the fallback collapses to
  today's behavior.
- Coolify deployments that *don't* set the override vars also continue to work — the
  fallback path is byte-identical to today's hardcoded values.
- No change to Django settings, no change to `python-decouple` defaults.
