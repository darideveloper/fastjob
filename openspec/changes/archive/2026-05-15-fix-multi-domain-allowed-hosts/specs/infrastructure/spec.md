# infrastructure Spec Delta

## MODIFIED Requirements

### Requirement: Dynamic Host Security
The application MUST dynamically adapt `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, and `SITE_DOMAIN` to the deployment URL, and MUST support deployments that serve more than one public domain simultaneously (e.g. a vanity domain plus the Coolify-managed subdomain).

When the operator does NOT supply explicit overrides, the configuration MUST fall back
to deriving these settings from Coolify's `SERVICE_FQDN_WEB` so the
`Coolify One-Click Compatibility` requirement is preserved.

When the operator DOES supply explicit overrides (via Coolify UI env vars, a `.env`
file, or any other Compose-visible mechanism), those values MUST take precedence over
the auto-derived defaults, on every service that reads them (`web`, `celery_worker`,
`celery_beat`).

#### Scenario: Single-domain Coolify deployment (no overrides)

- **Given** Coolify assigns `https://fastjob-xyz.coolify.io` to the `web` service
- **AND** the operator has NOT set `ALLOWED_HOSTS`, `SITE_DOMAIN`, or
  `CSRF_TRUSTED_ORIGINS` as project-level env vars
- **When** the application starts
- **Then** `ALLOWED_HOSTS` MUST include `fastjob-xyz.coolify.io`
- **AND** `CSRF_TRUSTED_ORIGINS` MUST include `https://fastjob-xyz.coolify.io`
- **AND** `SITE_DOMAIN` MUST equal `fastjob-xyz.coolify.io`

#### Scenario: Multi-domain deployment with operator overrides

- **Given** Coolify assigns `https://fastjob.apps.darideveloper.com` to the `web` service
- **AND** the operator has set, as Coolify project-level env vars (Runtime enabled):
  - `ALLOWED_HOSTS=fastjob.es,fastjob.apps.darideveloper.com,localhost,127.0.0.1`
  - `CSRF_TRUSTED_ORIGINS=https://fastjob.es,https://fastjob.apps.darideveloper.com`
  - `SITE_DOMAIN=fastjob.es`
- **When** the application starts and a request arrives with `Host: fastjob.es`
- **Then** the request MUST NOT be rejected with `DisallowedHost`
- **AND** a CSRF-protected POST originating from `https://fastjob.es` MUST be accepted
- **AND** absolute URLs generated by Django (transactional emails, OAuth callbacks,
  unsubscribe links emitted from Celery workers) MUST use `https://fastjob.es` as their
  base.

#### Scenario: Background tasks honor the operator-chosen canonical domain

- **Given** the operator has set `SITE_DOMAIN=fastjob.es` as described above
- **When** the Celery worker generates an unsubscribe link for an outgoing email
- **Then** the link MUST be rooted at `https://fastjob.es/...`
- **AND** MUST NOT be rooted at the Coolify-managed subdomain.

#### Scenario: Local developer workflow remains unchanged

- **Given** a developer has the project's standard `.env` (per `.env.example`) defining
  `ALLOWED_HOSTS=localhost,127.0.0.1,fastjob.localhost`,
  `SITE_DOMAIN=fastjob.localhost:8000`, and
  `CSRF_TRUSTED_ORIGINS=http://fastjob.localhost:8000,https://fastjob.localhost`
- **When** they run `docker compose up`
- **Then** the rendered container environment MUST use those `.env` values verbatim
- **AND** MUST NOT be overridden by any Compose-level default tied to
  `SERVICE_FQDN_WEB`.

## ADDED Requirements

### Requirement: Host Configuration Override Precedence
The `docker-compose.yml` orchestration MUST expose `ALLOWED_HOSTS`, `SITE_DOMAIN`, and `CSRF_TRUSTED_ORIGINS` as opt-overrideable environment variables on every service that consumes them.

Scope per setting:

- `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` are HTTP-layer concerns and MUST be
  overrideable on the `web` service only. They MUST NOT be defined on
  `celery_worker` or `celery_beat`, which do not serve HTTP requests.
- `SITE_DOMAIN` is a URL-building concern read at runtime by both HTTP request
  handlers and background tasks, so it MUST be overrideable on `web`,
  `celery_worker`, and `celery_beat`, and MUST resolve to the same value on all
  three services.

"Opt-overrideable" means: when the variable is supplied to Compose (via `.env`, shell
export, or PaaS UI), that value MUST flow unchanged into the container; when the
variable is absent, Compose MUST fall back to a defined default derived from
`SERVICE_FQDN_WEB`.

#### Scenario: Override precedence on the web service

- **Given** the `.env` file (or PaaS env) sets `ALLOWED_HOSTS=a.example,b.example`
- **AND** Compose's web-service entry uses `${ALLOWED_HOSTS:-<fallback>}` form
- **When** Compose renders the container env
- **Then** the container receives `ALLOWED_HOSTS=a.example,b.example`
- **AND** the fallback string is NOT used.

#### Scenario: Override precedence on celery services

- **Given** the operator sets `SITE_DOMAIN=fastjob.es`
- **When** the `celery_worker` and `celery_beat` containers start
- **Then** both services MUST receive `SITE_DOMAIN=fastjob.es` (same value as the
  `web` service)
- **AND** absolute URLs they emit (e.g. unsubscribe links) MUST match those produced by
  the `web` service for the same logical resource
- **AND** the celery services MUST NOT have `ALLOWED_HOSTS` or `CSRF_TRUSTED_ORIGINS`
  defined, since they do not serve HTTP.

#### Scenario: Fallback when no override is supplied

- **Given** the operator has set `SERVICE_FQDN_WEB=foo.coolify.io` only
- **AND** has NOT set `ALLOWED_HOSTS`, `SITE_DOMAIN`, or `CSRF_TRUSTED_ORIGINS`
- **When** Compose renders the container env
- **Then** `ALLOWED_HOSTS` MUST resolve to `foo.coolify.io,localhost,127.0.0.1`
- **AND** `SITE_DOMAIN` MUST resolve to `foo.coolify.io`
- **AND** `CSRF_TRUSTED_ORIGINS` MUST resolve to `https://foo.coolify.io`
- **AND** the values MUST be byte-identical to those produced by the prior
  unconditional-assignment form, preserving `Coolify One-Click Compatibility`.
