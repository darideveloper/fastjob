# Design: Multi-Domain Host Configuration

## Context

Three settings — `ALLOWED_HOSTS`, `SITE_DOMAIN`, `CSRF_TRUSTED_ORIGINS` — currently have
a hardcoded compose-level dependency on Coolify's `SERVICE_FQDN_WEB`. That single FQDN
is sufficient for the original "one-click Coolify import" requirement, but not for the
real-world case where the app must serve **multiple** public domains (a vanity domain
plus the Coolify-managed subdomain, or a brand-migration period where both old and new
domains are live).

This design picks the lightest fix that preserves all existing requirements.

## Options considered

### Option A — Make compose vars opt-overrideable via `${VAR:-fallback}` (chosen)

```yaml
- ALLOWED_HOSTS=${ALLOWED_HOSTS:-${SERVICE_FQDN_WEB},localhost,127.0.0.1}
- SITE_DOMAIN=${SITE_DOMAIN:-${SERVICE_FQDN_WEB}}
- CSRF_TRUSTED_ORIGINS=${CSRF_TRUSTED_ORIGINS:-https://${SERVICE_FQDN_WEB}}
```

**Pros**
- Three-line diff. No Python changes. No migration.
- Backward-compatible: when overrides are unset (fresh Coolify import, CI, ad-hoc
  `docker compose up` with only `.env.example` set) the rendered values are
  **byte-identical** to today, so `Coolify One-Click Compatibility` is preserved.
- Local dev keeps working unchanged because the developer's `.env` already supplies the
  three vars (see `.env.example:3,37,69`).
- Operator workflow is the obvious one — declare the var in Coolify UI, redeploy.

**Cons**
- Operator must remember to set three correlated variables. Mitigated by documenting
  them as a group in `.env.example` and the deployment runbook (`tasks.md` §4).

### Option B — Compose builds `ALLOWED_HOSTS` from a list of `SERVICE_FQDN_WEB_*` vars

Would require Coolify to expose multiple FQDN slots per service. Coolify (as of v4 beta)
exposes a single primary FQDN per service. Implementing this would require either
brittle shell concatenation inside compose (no native list type) or a wrapper entrypoint
that builds the env at container start. Disproportionate complexity for a config issue.
Rejected.

### Option C — Move host parsing into Django (compute ALLOWED_HOSTS from `EXTRA_HOSTS` + `SERVICE_FQDN_WEB`)

Pushes deployment concerns into application code; couples `settings.py` to Coolify's
naming. Rejected on the principle that infrastructure config belongs in the compose
layer.

## Why Option A is safe for local

The compose substitution `${ALLOWED_HOSTS:-…}` resolves to the *fallback* only when the
variable is unset **or empty**. Two paths:

1. Developer with `.env` (default) — `.env` sets `ALLOWED_HOSTS=localhost,127.0.0.1,fastjob.localhost`.
   Compose substitutes that exact value. Today's behavior is also exactly that, because
   `SERVICE_FQDN_WEB` is empty in local and the previous line `${SERVICE_FQDN_WEB},localhost,127.0.0.1`
   ends up as `,localhost,127.0.0.1` (with a leading empty entry — actually a latent bug
   in the current setup, but harmless because Django ignores empty strings in `Csv()`).
   The new form is strictly cleaner.
2. Developer without `.env` — fallback path activates. With `SERVICE_FQDN_WEB` unset,
   the fallback renders `,localhost,127.0.0.1` — same latent empty-leading entry as
   today, same harmless behavior. No regression.

## Why Option A is safe for prod

Three sub-paths:

1. Coolify deployment **without** the new UI vars set (existing one-click users) —
   fallback activates, renders `${SERVICE_FQDN_WEB},localhost,127.0.0.1`, byte-for-byte
   today's value. No regression.
2. Coolify deployment **with** the new UI vars set (this issue's deployment) —
   override wins, Django sees `fastjob.es,fastjob.apps.darideveloper.com,localhost,127.0.0.1`.
   Bug fixed.
3. Mis-configured deployment where operator sets `ALLOWED_HOSTS` but forgets
   `CSRF_TRUSTED_ORIGINS` — host check passes but CSRF rejects POSTs from the new
   domain. This is a *visible*, debuggable failure (Django emits a clear log line and
   form submissions fail with a recognizable 403), and is documented in the operator
   runbook (`tasks.md` §4) as a three-var set. Acceptable.

## Worker/Beat alignment

`celery_worker` and `celery_beat` already carry `SITE_DOMAIN=${SERVICE_FQDN_WEB}`
(`docker-compose.yml:117` and `:151`) — these lines are within the scope of the
in-flight `fix-celery-site-url-env` proposal (which `openspec list` reports as 0/3
tasks but whose target lines are already present in the compose file). This change
extends those exact lines with the `${VAR:-…}` override form so that absolute URLs
generated by the slow-drip mailing engine (e.g. unsubscribe links — a `mailing`
capability concern) use the canonical operator-chosen domain rather than the Coolify
subdomain.

Important scoping note: only `SITE_DOMAIN` is updated on `celery_worker` and
`celery_beat`. `ALLOWED_HOSTS` and `CSRF_TRUSTED_ORIGINS` are HTTP-layer settings that
the celery services do not read (they do not handle HTTP requests, and the `web`
service is the only one with an HTTP port published). Adding those vars to the celery
services would be inert noise and would risk implying — incorrectly — that the celery
services serve HTTP.

`fix-celery-site-url-env` and this change touch overlapping lines but with
non-conflicting intents (one *introduces* the celery `SITE_DOMAIN`, the other *converts
it to the override form*). Reviewers should land them in series; if this change merges
first, the existing celery `SITE_DOMAIN` lines simply gain the `${VAR:-…}` wrapper.

## Risk assessment

| Risk | Likelihood | Severity | Mitigation |
|---|---|---|---|
| Operator sets `ALLOWED_HOSTS` but omits `localhost,127.0.0.1`, breaking Docker healthchecks | Medium | Medium | Documented in `.env.example` comment and `tasks.md` §4.1 — value must include `localhost,127.0.0.1` |
| Operator sets `ALLOWED_HOSTS` but forgets `CSRF_TRUSTED_ORIGINS` | Medium | Low | Visible failure (clear 403 on POST). Runbook lists all three vars together. |
| `SITE_DOMAIN` divergence between `web` and `celery_*` services | Low | Medium | Tasks 1.4 / 1.5 enforce identical `${VAR:-…}` pattern for `SITE_DOMAIN` across all three services. Spec scenario "Override precedence on celery services" enforces same resolved value. |
| Operator adds `ALLOWED_HOSTS` or `CSRF_TRUSTED_ORIGINS` to celery services thinking it's required for parity | Low | Low | Tasks 1.4 / 1.5 explicitly state the scope: only `SITE_DOMAIN` on celery. Spec requirement enumerates per-setting scope. |
| Change in `SERVICE_FQDN_WEB` semantics in a future Coolify release | Low | Low | Fallback isolates us — operators can always pin via the override vars. |

## Out of scope

- Auto-detecting domains from request headers (would weaken host-injection defense).
- Wildcard subdomain support (`*.fastjob.es`) — not requested; trivially supported by
  listing each subdomain in `ALLOWED_HOSTS` if needed later.
- Migrating off `python-decouple` to Pydantic settings or similar — orthogonal.
- Any change to the OAuth callback URLs registered in Google/Microsoft consoles. Those
  are tied to `SITE_DOMAIN`; if the operator switches `SITE_DOMAIN` from the Coolify
  subdomain to `fastjob.es`, they MUST also re-register the callback URLs in the
  respective consoles. Called out in the rollout runbook but enacted manually.
