# Change: Chunked Excel import with live progress in the admin

## Why
Once `fix-excel-import-timeout` (now archived) shipped, the next operator-visible problem became the importer itself. A 55 MB / ~150,000-row company-import xlsx takes ~7 minutes to process inside `import_companies_from_xlsx`'s single `with transaction.atomic():` block (`apps/companies/importers.py:47`), with `update_or_create` running per row. Throughout that window the admin batch detail page at `/admin/companies/companyimportbatch/<id>/change/` shows `Procesando` with all counters at zero and no indication that the worker is alive — observed live on import #19 on 2026-05-07. Operators repeatedly think the process has hung, refresh the page, and at best wait blindly.

The two problems are independent: the upload-timeout proposal solved request-thread blocking; this proposal solves *worker-thread invisibility* and the underlying per-row-DB-call slowness that made the invisibility painful in the first place. The importer must commit progress visibly chunk-by-chunk, the writes inside each chunk must be bulk operations, and the admin must surface live progress without manual refresh.

## What Changes
- **Chunked commit semantics in the importer.** Replace the single `with transaction.atomic():` in `import_companies_from_xlsx` with one `transaction.atomic()` per chunk of `COMPANY_IMPORT_CHUNK_SIZE` rows (default 1000). Each chunk commits independently, so its row inserts AND its updated counter fields become visible to the admin polling endpoint as soon as the chunk finishes.
- **Bulk DB writes per chunk.** Replace per-row `Company.objects.update_or_create` with a single `Company.objects.filter(email__in=…).values_list("email", "id")` lookup followed by `bulk_create(ignore_conflicts=True)` for new rows and `bulk_update(...)` for existing rows. A 1000-row chunk drops from ~4000 SQL roundtrips to ~3.
- **Two new fields on `CompanyImportBatch`:** `total_rows` and `processed_rows` (both `PositiveIntegerField`, default `0`). The admin uses them as numerator/denominator for a progress bar.
- **Preflight row count, with fallback for non-conformant xlsx producers.** Before chunk processing starts, `process_company_import` opens the workbook in `read_only=True`, reads `ws.max_row` (minus header), clamps it to a sane upper bound, and saves it as `batch.total_rows` so the dashboard immediately gets a meaningful denominator. **When `ws.max_row` is unreliable** — `None` (the producer omitted the `<dimension>` element entirely) or `<= 1` (the producer wrote a placeholder dimension like `<dimension ref="A1:B1"/>` despite having many more rows) — the preflight MUST call `ws.reset_dimensions()` to clear openpyxl's internal `_max_row` cap and then stream-count the rows via `iter_rows`. The reset is critical because `iter_rows` honors `self.max_row` as an upper bound, so a placeholder dimension would otherwise stop the iteration at row 1 and the fallback would also yield 0. Without this fix the user observed `Total rows = 0` after upload — the live progress widget had no denominator and stayed at `0/0` until reconciliation pinned it to the post-import processed count.
- **Live progress JSON endpoint.** `GET /admin/companies/companyimportbatch/<int:object_id>/progress/` returns `{"status", "total_rows", "processed_rows", "created_count", "updated_count", "blacklisted_skipped", "error_count"}` for the batch. Auth gated by `self.admin_site.admin_view(...)`.
- **Admin change-form auto-refresh.** Override the admin change-form template for `CompanyImportBatchAdmin` to add a small inline JS poller (2 s interval) that calls the progress endpoint and updates a progress bar + counter widgets in place. Polling stops when status reaches `COMPLETED` / `FAILED`, and the page reloads once so the standard admin view (file field, error_log, status flag) reflects the final state.
- **`bust_filter_caches()` move.** The cache-bust call is moved out of `import_companies_from_xlsx` and into `process_company_import` (called once after the importer returns successfully), so per-chunk commits don't over-bust the cache 150 times per import.
- **BREAKING (semantics)**: chunked commits trade rollback-on-failure for in-flight visibility. If the worker crashes mid-import, rows up to the last successful chunk are persisted. Re-running the same file is safe because the importer is idempotent on `Company.email` (existing rows go through the bulk-update path, not the bulk-create path).
- **Backward-compat**: `import_companies_from_xlsx(file_path)` remains callable with just a path. The `batch=None` default skips the per-chunk progress writes; the chunking and bulk-write behavior happens regardless. Existing callers and tests don't need to change.
- **Diagnostic upload-view error path.** Broaden the exception handler in `CompanyAdmin.import_xlsx_view` so failures other than `OSError` / `SuspiciousFileOperation` (notably `django.db.utils.DatabaseError` from schema drift, e.g. an unapplied migration) no longer surface as an opaque generic-500 message ("Error al subir el archivo. Por favor inténtalo de nuevo."). Instead, the view MUST log the traceback and return a JSON error payload that names the underlying exception class and message, so operators can immediately see *why* the upload failed. This was discovered post-implementation when migration `0011_companyimportbatch_progress` had not been applied locally and `CompanyImportBatch.objects.create(...)` raised `ProgrammingError: column "total_rows" does not exist`, but the admin UI showed only the generic fallback string from the upload XHR.

## Impact
- Affected specs:
  - `companies` — MODIFY `Asynchronous Excel Import Processing` (add live-progress clauses); MODIFY `Enhanced Spanish XLSX Importer` (clarify chunked / bulk semantics and idempotent re-run guarantee); ADD `Chunked Import Progress Tracking`; ADD `Live Progress Dashboard for Import Batches`.
- Affected code:
  - `apps/companies/models.py` — two new `PositiveIntegerField` columns on `CompanyImportBatch`
  - `apps/companies/migrations/` — new `0011_companyimportbatch_progress.py`
  - `apps/companies/importers.py` — chunked commit + bulk write rewrite
  - `apps/companies/tasks.py` — preflight `total_rows`, pass `batch` and `chunk_size` to importer, `bust_filter_caches()` moved here
  - `apps/companies/admin.py` — register progress URL, override `change_form_template`, add `progress_json` view, surface `total_rows` / `processed_rows` in `list_display` and `readonly_fields`; **broaden the upload-view exception handler in `import_xlsx_view` so non-file-write exceptions (e.g. `DatabaseError` from schema drift) return a diagnostic JSON `error` payload instead of an opaque generic 500**
  - `templates/admin/companies/companyimportbatch/change_form.html` — new file with progress widget + polling JS
  - `config/settings.py` — add `COMPANY_IMPORT_CHUNK_SIZE`
  - tests: `apps/companies/tests/test_importers.py`, `apps/companies/tests/test_tasks.py` (incl. the preflight-fallback regression for unreliable `ws.max_row`), new `apps/companies/tests/test_admin_progress.py`, extension to `apps/companies/tests/test_admin_import_view.py` to cover the diagnostic upload-view error path
